# PKCS#11 Coverage-Gap Plan

Cross-referenced against:
- A local OASIS PKCS#11 v3.2 spec mirror + the `pkcs11-proxy-ng` reference
  proxy implementation (52 parameter shapes, 62 C_* functions, 30+
  integration tests)
- A local TCS git mirror of the spec headers and prose
- `src/pkcs11_check/testcases/` — current 287 test files

This is a planning artifact, not a status doc. Items here are verified — when
this doc says "1 hit" or "0 hits" it means `grep` against the codebase
confirmed it.

## Methodology

Initial gap candidates were generated by three parallel explore agents.
Each candidate was then re-checked against the actual codebase:

- Reading the actual files where 1-3 mentions appeared
- Confirming `def test_...` density matches the claim
- Distinguishing **probe-only** coverage (function-exists checks) from
  **behavioral** coverage (actually exercises the path)

The initial gap list of 10 Tier-1 items shrank to 6 verified gaps once
this verification ran. The agents over-counted gaps in: CKM_RSA_AES_KEY_WRAP
(already covered), SLH-DSA SHAKE parameter sets (fully covered in ACVP),
IKE 4 variants (covered), ECMQV (covered), SSL3/WTLS key-mat (covered),
TLS extended master (covered), C_SessionCancel (covered).

## Verified Tier 1 gaps (the real list)

### T1.3 — Same-session multi-thread `*Init` race
**Status:** test_threading.py exists but every test opens a *new session per
thread* (`open_session()` inside each task). The actual race —
two threads attempting `C_EncryptInit` on the **same** `CK_SESSION_HANDLE` —
is not tested.

**Why it matters:** spec requires `CKR_OPERATION_ACTIVE` on the loser of the
race; some modules return `CKR_OK` to both and silently corrupt state. NSS
softoken has had real CVEs in this area.

**Proposed work:** new file `test_session_op_race.py` (~4 tests, non-destructive):
- Two threads, same session, both call `C_DigestInit(CKM_SHA256)` after a
  barrier-sync. Exactly one must succeed; the loser must return
  `CKR_OPERATION_ACTIVE` (not `CKR_OK` with corrupted state).
- Same with `C_EncryptInit(CKM_AES_ECB)`.
- One thread mid-`C_EncryptUpdate`, another calls `C_EncryptInit` — expect
  `CKR_OPERATION_ACTIVE` on the second-init thread, and the in-flight
  update must complete cleanly.
- One thread `C_SignInit` + `C_Sign`, another thread `C_DigestInit` —
  expect `CKR_OPERATION_ACTIVE` since both are crypto ops on one session.

### T1.4 — `C_GetMechanismInfo` behavioral cross-validation
**Status:** `test_mech_flags.py` validates `min_key_size <= max_key_size`
and that the **registry-expected** flags are a subset of reported flags.
It does **not** verify that *every reported flag corresponds to actual
working behavior*. A module that advertises `CKF_ENCRYPT` for a mechanism
it cannot encrypt with is the single most common conformance bug.

**Proposed work:** add `TestMechFlagBehavioralConformance` class in
`test_mech_flags.py` (~one parametrized test per flag, parametrized over
mechanism list — ~50 mechs × 10 flags ~ 500 test ids, all skip when flag
not set or key material unavailable):
- For every mech advertising `CKF_ENCRYPT`: try `C_EncryptInit` with a
  minimal valid key. Expect *not* `CKR_MECHANISM_INVALID` and *not*
  `CKR_FUNCTION_NOT_SUPPORTED`. (Other errors like `CKR_KEY_TYPE_INCONSISTENT`
  imply key-pairing issues, not flag-lying.)
- Same for `CKF_DECRYPT`, `CKF_SIGN`, `CKF_VERIFY`, `CKF_DIGEST`,
  `CKF_GENERATE`, `CKF_GENERATE_KEY_PAIR`, `CKF_WRAP`, `CKF_UNWRAP`,
  `CKF_DERIVE`, `CKF_ENCAPSULATE`, `CKF_DECAPSULATE`.

### T1.7 — `CKO_PROFILE` behavioral conformance
**Status:** test_profiles.py has 4 tests: enumeration, attribute reads,
known-profile-ids, baseline-or-extended-present. None verify that, given
profile X is advertised, the module **actually supports** the spec-mandated
mechanism set for profile X. This is exactly the "no false advertising"
check that profiles exist to enable.

**Proposed work:** add `TestProfileBehavioralConformance` class to
test_profiles.py:
- New module `pkcs11_check.compliance.profile_tables` mapping each profile
  ID (CKP_BASELINE_PROVIDER, CKP_EXTENDED_PROVIDER, CKP_AUTHENTICATION_TOKEN,
  CKP_PUBLIC_CERTIFICATES_TOKEN, and v3.2 PQ profiles) → required mechanism
  set + required function set, transcribed from
  `pkcs11-profiles-v3.2.html`.
- Parametrized test: for every advertised profile, every required mech
  must be in `C_GetMechanismList`. Failure → pytest.fail (it's a spec
  conformance bug).

### T1.8 — `CKA_ALWAYS_AUTHENTICATE` enforcement flow
**Status:** test_attribute_enforcement.py has `test_always_authenticate_readable`
and `test_always_authenticate_set_on_keygen` (recognition only). The
docstring at line 580 explicitly says "Complex to test and many [modules
skip]" — the operational enforcement (sign without CKU_CONTEXT_SPECIFIC
fails; sign with re-auth succeeds; second sign requires fresh re-auth)
is untested.

**Proposed work:** new file `test_always_authenticate.py` (~6 tests, all
non-destructive — uses the existing user PIN as the context-specific PIN,
which is the standard default):
- Generate RSA-2048 keypair with `CKA_ALWAYS_AUTHENTICATE=TRUE`; skip if
  module rejects the attribute on keygen.
- `C_SignInit` then `C_Sign` without context-specific login: expect
  `CKR_USER_NOT_LOGGED_IN`.
- `C_Login(CKU_CONTEXT_SPECIFIC, pin)` then `C_SignInit` then `C_Sign`:
  expect success.
- Immediately repeat: re-auth is consumed, second sign must require fresh
  re-auth.
- Wrong PIN to context-specific: `CKR_PIN_INCORRECT`, key remains unusable.
- `CKU_CONTEXT_SPECIFIC` without prior `CKU_USER` login: expect
  `CKR_OPERATION_NOT_INITIALIZED` or `CKR_USER_NOT_LOGGED_IN`.

### T1.9 — Stateful hash sig exhaustion (XMSS small-tree)
**Status:** test_stateful_sigs.py docstring says "Tests sign minimally to
avoid exhaustion."  The exhaustion path itself (signing past the leaf
count returns `CKR_KEY_EXHAUSTED`, not `CKR_OK` with leaf reuse, not
SIGSEGV) is the security-critical case.

**Note on destructiveness:** generating a tiny H=2 XMSS tree and signing 5
times to drain it does *not* require token init/finalize and does not
modify any state outside the generated key. The key is destroyed in
`finally`. By the project convention (`@destructive` = ops that touch
token state like `C_InitToken` / PIN changes / `C_Finalize`), this is
**non-destructive**.

**Proposed work:** add `TestXmssExhaustion` class to test_stateful_sigs.py
(~3 tests):
- Generate XMSS keypair with smallest parameter set (H=2 — 4 leaves).
- Sign 1, 2, 3, 4 — all expected to succeed.
- Sign 5: expect `CKR_KEY_EXHAUSTED` (v3.2 CKR added for this purpose).
- Sign 6 (post-exhaustion): also expect `CKR_KEY_EXHAUSTED`, never
  `CKR_OK` (silent leaf reuse = security gap).

### T1.10 — Output buffer corner cases beyond input-size testing
**Status:** test_buffers.py covers input sizes (empty, 1B, block,
boundary, 1MB). test_ckr_null_params.py covers per-function NULL parameter
behavior. Neither covers the *interaction* edge cases.

**Proposed work:** extend test_buffers.py with `TestBufferEdgeCases`
class (~6 tests, non-destructive):
- `pBuffer=NULL` and `*pulSize` left as input garbage — must populate
  `*pulSize` with required size; spec says CKR_OK on the probe.
- `pBuffer=non-NULL` with `pulSize=NULL` — must be `CKR_ARGUMENTS_BAD`.
- `C_SignFinal` with `*pulSize=0` and `pBuffer=non-NULL` — should be
  `CKR_BUFFER_TOO_SMALL`, *and* a subsequent `C_SignFinal` with proper
  buffer must complete (state preserved on TOO_SMALL).
- Three sequential `CKR_BUFFER_TOO_SMALL` retries followed by correct-size
  call — state must remain intact through all three retries.
- `*pulSize = 0xFFFFFFFFFFFFFFFF` (max) — must not allocate or attempt
  to write that much; expect CKR_OK and a small written size.
- `C_EncryptUpdate` with too-small output buffer followed by
  `C_EncryptFinal` with proper buffer — verify which behavior the module
  follows (spec ambiguous; record per-module).

## Tier 4 — Items deferred per user instruction

These were on the initial plan but are destructive (touch C_Initialize,
mutex callbacks, token state):

- **T1.1 `CK_C_INITIALIZE_ARGS` matrix** — 4 init modes × callback
  variants. Requires `C_Initialize`/`C_Finalize` cycles ⇒ destructive.
- **T1.2 Reentrancy from mutex callbacks** — requires custom callbacks
  passed into `C_Initialize` ⇒ destructive.

Per the current round's instruction, these are **deferred**. They remain
high-leverage if revisited.
