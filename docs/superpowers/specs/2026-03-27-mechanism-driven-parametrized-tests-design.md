# Mechanism-Driven Parametrized Tests

**Date:** 2026-03-27
**Status:** Design, pending review

## Goal

Create a comprehensive, mechanism-driven test system that automatically tests every advertised PKCS#11 mechanism based on its CKF_* flags, with pre-generated known-answer test vectors, negative tests for error handling, and composite multi-step workflow tests.

## Architecture Overview

```
Layer 1: Test Data (JSON vectors in repo)
    testcases/data/mechanism_vectors/*.json
    scripts/generate_mechanism_vectors.py

Layer 2: Mechanism Registry (declarative config)
    testcases/mechanism_registry.py

Layer 3: Operation Tests (one file per operation type)
    testcases/test_mech_keygen.py      — CKF_GENERATE / CKF_GENERATE_KEY_PAIR
    testcases/test_mech_encrypt.py     — CKF_ENCRYPT + CKF_DECRYPT
    testcases/test_mech_sign.py        — CKF_SIGN + CKF_VERIFY
    testcases/test_mech_digest.py      — CKF_DIGEST
    testcases/test_mech_wrap.py        — CKF_WRAP + CKF_UNWRAP
    testcases/test_mech_derive.py      — CKF_DERIVE
    testcases/test_mech_kem.py         — CKF_ENCAPSULATE + CKF_DECAPSULATE
    testcases/test_mech_negative.py    — wrong key types, sizes, permissions
    testcases/test_mech_probe.py       — unknown/vendor mechanisms: no-crash init

Layer 4: Composite Lifecycle Tests
    testcases/test_mech_lifecycle.py   — 11 multi-step workflow patterns
```

## Layer 1: Test Data

### Storage

Pre-generated known-answer test (KAT) vectors stored in `src/pkcs11_check/testcases/data/mechanism_vectors/`. One JSON file per mechanism or mechanism family. Files are committed to the repo and loaded dynamically at test collection time — adding a new JSON file automatically adds it to the next test run.

### Generator Script

`scripts/generate_mechanism_vectors.py` uses the `cryptography` Python library to produce vectors:

```python
# Usage:
# uv run python scripts/generate_mechanism_vectors.py --family aes_gcm --output src/pkcs11_check/testcases/data/mechanism_vectors/aes_gcm.json
# uv run python scripts/generate_mechanism_vectors.py --all  # regenerate all
```

The script is idempotent — uses fixed seeds for reproducibility. Adding a new mechanism family means adding a generator function to the script and running it once.

## Layer 2: Mechanism Registry

### File: `src/pkcs11_check/testcases/mechanism_registry.py`

Declarative dataclass mapping mechanism IDs to test configuration:

```python
@dataclass(frozen=True)
class MechConfig:
    """Configuration for testing a specific mechanism."""
    key_type: int                          # CKK_AES, CKK_RSA, etc.
    keygen_mech: int                       # mechanism to generate the right key
    key_sizes: tuple[int, ...]             # valid key sizes in bits
    is_keypair: bool                       # True for asymmetric (uses C_GenerateKeyPair)
    param_packer: str | None               # name of packer function: "mech_gcm", "mech_pss", etc.
    param_factory: str | None              # name of function that creates default test params
    block_size: int | None                 # block size in bytes (16 for AES block modes)
    vector_file: str | None                # path to JSON vectors file (relative to data dir)
    input_constraint: str                  # "block_aligned", "any", "digest_only", "none"
    notes: str = ""                        # human-readable notes

# The registry: CKM int → MechConfig
MECHANISM_REGISTRY: dict[int, MechConfig] = {
    CKM_AES_ECB: MechConfig(
        key_type=CKK_AES, keygen_mech=CKM_AES_KEY_GEN,
        key_sizes=(128, 192, 256), is_keypair=False,
        param_packer=None, param_factory=None,
        block_size=16, vector_file="aes_ecb.json",
        input_constraint="block_aligned",
    ),
    CKM_AES_GCM: MechConfig(
        key_type=CKK_AES, keygen_mech=CKM_AES_KEY_GEN,
        key_sizes=(128, 192, 256), is_keypair=False,
        param_packer="mech_gcm", param_factory="default_gcm_params",
        block_size=None, vector_file="aes_gcm.json",
        input_constraint="any",
    ),
    CKM_RSA_PKCS_OAEP: MechConfig(
        key_type=CKK_RSA, keygen_mech=CKM_RSA_PKCS_KEY_PAIR_GEN,
        key_sizes=(2048, 3072, 4096), is_keypair=True,
        param_packer="mech_oaep", param_factory="default_oaep_params",
        block_size=None, vector_file="rsa_oaep.json",
        input_constraint="any",
    ),
    # ... 50+ entries covering all mechanism families
}
```

### Fallback for unregistered mechanisms

Mechanisms not in the registry get a "probe" test: call `C_*Init` with the mechanism, verify it either returns CKR_OK or a valid error code (not a crash/segfault).

### Helper: discover_test_params()

```python
def discover_test_params(
    raw: RawPKCS11, slot_id: int, flag_filter: int
) -> list[tuple[int, dict, MechConfig | None]]:
    """Discover all mechanisms matching flag_filter, return (mech_id, info, config) tuples.

    Filters by min/max key size from C_GetMechanismInfo.
    Returns MechConfig=None for unregistered mechanisms (probe tests).
    """
```

This is the core discovery function used by all test files.

## Layer 3: Operation Tests

### Test Discovery Pattern (shared across all files)

```python
def _collect_mechanisms(rs, flag):
    """Collect (mech_id, mech_name, key_size, config, vectors) tuples for parametrization."""
    params = []
    for mech_id in get_mechanism_list(rs.raw, rs.slot_id):
        info = get_mechanism_info(rs.raw, rs.slot_id, mech_id)
        if not (info["flags"] & flag):
            continue
        config = MECHANISM_REGISTRY.get(mech_id)
        if config is None:
            continue  # unregistered → handled by probe test
        vectors = load_vectors(config.vector_file) if config.vector_file else []
        for key_size in config.key_sizes:
            if key_size < info["min_key_size"] or key_size > info["max_key_size"]:
                continue
            params.append((mech_id, ckm_name(mech_id), key_size, config, vectors))
    return params
```

class TestNegativeWrongKeyType:
    """Test that using wrong key type for a mechanism is rejected."""

    @pytest.mark.parametrize("mech_id,wrong_key_type", WRONG_KEY_TYPE_PAIRS)
    def test_encrypt_wrong_key_type(self, p11_raw_session, mech_id, wrong_key_type):

## Test Markers

All mechanism-driven tests get `@pytest.mark.mechanism_coverage` marker. Individual files also get operation markers:

- `test_mech_encrypt.py`: `pytest.mark.encrypt`
- `test_mech_sign.py`: `pytest.mark.sign`
- `test_mech_lifecycle.py`: `pytest.mark.lifecycle`
- `test_mech_negative.py`: `pytest.mark.negative`

## Expected Test Counts (per module)

For a module like Kryoptic (168 mechanisms, ~120 invoked):
- Keygen: ~30 tests (one per keygen mechanism × sizes)
- Encrypt: ~60 tests (10 encrypt mechanisms × 3 sizes × 2 types)
- Sign: ~40 tests (8 sign mechanisms × 3 sizes + hash combos)
- Digest: ~15 tests (one per hash)
- Wrap: ~20 tests (wrap mechanisms × sizes)
- Derive: ~25 tests (ECDH × KDFs + HKDF + PBKDF2)
- KEM: ~10 tests (ML-KEM × 3 param sets + roundtrip)
- Negative: ~40 tests (7 wrong-key-type × operation + param invalid)
- Probe: ~20 tests (unregistered mechanisms)
- Lifecycle: ~15 tests (11 patterns + variants)
- KAT vectors: ~150 tests (across all mechanism families with vectors)
- **Total: ~425 new tests per module**

For a module like SoftHSM2 (80 mechanisms): ~250 new tests.

## Out of Scope

- Stress/performance testing (separate concern)
- Wycheproof vector integration (already exists in separate test files)
- NIST CAVP/ACVP integration (already exists in separate test files)
- Module-specific quirk handling (mechanism_registry is module-agnostic)
